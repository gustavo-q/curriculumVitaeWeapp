# 简历制作 · curriculumVitaeWeapp

一个微信小程序版的在线简历工具，功能对照 [curriculumVitae](../curriculumVitae)（纯前端网页版，
仿 polebrief.com）逐项移植：18 套模板、区块 + 条目模型、三种条目排版、单栏与左右两栏布局、
所见即所得纸面编辑、A4 软分页、智能压缩到一页、照片外形与证件照比例、撤销重做、JSON 备份迁移。

**所有数据都保存在本机（wx storage），不请求任何后端。**

---

## 快速开始

用微信开发者工具打开本目录即可（`project.config.json` 已配好，appid 为测试号 `touristappid`）。

小程序开发者工具的「服务端口」默认是关闭的，本套验证不需要它；如需用官方自动化能力，
在工具 → 设置 → 安全设置里打开服务端口。

### 能力边界（为什么少了三种导出）

参考站的 PDF 走浏览器打印窗口、Word 走 HTML 转 `.doc`、HTML 导出为独立文件，
三者都依赖「可写文件系统 + 浏览器打印」，小程序运行在沙箱里没有这两样能力，因此：

- **PNG 长图**：保留。用 canvas 2d 按同一套排版几何绘制，2 倍高清，可直接存相册。
- **JSON 备份**：保留。改为「复制到剪贴板」，在新设备上用「导入」粘贴回来，跨设备迁移能力不变。
- PDF / Word / HTML：**不提供**。需要 PDF 时，可在网页版用同一份 JSON 备份打印。

### 数据模型

与参考站完全一致：

```
resume
├── resumeName / templateId / updateDatetime
├── pageLayout / headingTheme / borderTheme / fontFamily / fontSize …
├── baseInfo       基本信息（含 baseFields 开关列表）
├── personalPhoto* 照片（形状、边框、宽高、位置）
└── sections[]     区块 → items[] → { type: ONE | TWO | THREE, left / center / right }
```

`normalizeResume()` 负责补齐历史 / 导入数据，因此参考站导出的 JSON 备份可以直接导入小程序，
反之亦然（两者字段完全同构）。

存储键也与参考站同名：`pb_drafts_v1`（草稿列表）、`pb_current_v1`（当前草稿 id）。

### 排版引擎（`utils/layout.js`）

参考站在浏览器里靠「真实 DOM 测量」做两件事：A4 软分页、智能一页的反复试算。
小程序里如果照搬（`wx.createSelectorQuery()` 逐次测量），每试一组参数都要等一次渲染 + 一次
异步查询，二分几十轮下来界面会明显卡顿。

因此把纸张的排版规则在 JS 里实现了一遍：字号 / 行距 / 字距 / 边距 / 标题装饰高度 /
三种条目的 grid 轨道 / 单栏页眉 / 双栏信息栏，逐条对应 `paper.wxss` 的取值。
文本折行用 `canvas.measureText()`（离屏 canvas），没有 canvas 时退回「中文 1em、西文 0.52em」的估算。

于是三件事共用同一套几何：**屏幕渲染（WXML）、页数判定、PNG 导出**。
任何一边改了样式常量，另一边必须同步——`tools/check-geometry.cjs` 就是用来守住这条的。

### 屏幕与导出必须同源（一个影响很广的错位）

`layout.js` 的 `renderedFields()` 决定「引擎认为渲染了哪几栏」（进而决定列位与整页高度），
`paper.js` 的 `usesCol()` 决定「WXML 实际渲染哪几栏」。两者一旦分家，就会出现
**屏幕上文字靠左、导出的 PNG 里却靠右**这类错位。

`renderedFields()` 原本漏了 `editable` 这一维：只读态（预览页 / 首页缩略图 / 导出）
本应「空栏整体不渲染」，它却仍按条目类型补出空栏。于是 24 种「类型 × 填充组合」里
有 17 种与 `usesCol()` 不一致——最典型的是 THREE 条目只填正文时，屏幕按 1 个栏位
落在第 1 列，引擎却按 3 栏把正文算到第 2 列，**横向错位约一整列（331px）**。
现在 `check-logic.cjs` 用 48 种组合（2 种模式 × 3 种类型 × 8 种填充）守住这条同源约束。

### 布局实测为什么必须真跑浏览器

「底部面板被推到文档流末尾、要滑到最底才看得见」这类问题，**读源码是看不出来的**：
它取决于 `page` 根节点到底是不是限高的 flex 容器、以及未限高的 `scroll-view`
会不会把内容整条撑开。`check-editlayout.cjs` 的做法是先用同一份 `edit.wxss`
搭出等价 DOM，再分别按「修复前 / 修复后」渲染并量 `getBoundingClientRect()`：

```
修复前：panel.top = 1689   （视口 700 → 面板整个在屏幕外，复现问题）
修复后：panel.top = 294, bottom = 700   （贴合视口下沿）
```

命中测试（`elementFromPoint`）也一并断言，因此「按钮看得见但被遮罩挡住点不动」
这种问题会被直接抓出来。

### 断言有效性靠变异测试确认

新增断言必须证明「它真的能失败」。对四个曾经真实存在的缺陷注入回原始写法后，
对应断言确实转为失败，恢复后重新通过：

| 注入的缺陷 | 失败断言 |
| --- | --- |
| `render.js` 在 line/double 主题下读 `titleBox.size`（后者恒为 null） | 9 种标题装饰 × 居中开关 全部可导出 |
| `paper.js` 只读 `e.target.dataset`（文字叶子取不到标记） | 只有 field 时可从 currentTarget 补齐标记 |
| `section.wxml` 文字叶子去掉 `data-*` | section.wxml 的文字节点都带 data-sec/data-item |
| `edit.wxml` 的 `panel-body` 恢复成无条件 `scroll-y` | 面板滚动随拖动状态关闭 |

### 拖动排序时列表会跟着手指下滑（scroll-view 的隐性手势）

这是一个读 JS 永远看不出来的缺陷：手势状态机本身完全正确，问题在
`scroll-view` 是一个**原生滚动容器**，行上绑的 `bindtouchmove` 只是冒泡监听，
拦不住它自己的滚动。

于是「长按拖动排序」时，同一串纵向触摸同时被两处消费：

- 行按 `translateY(offsetY)` 跟手位移；
- `.panel-body` 按手势整体滚动。

两者叠加，拖动行以约两倍于手指的速度下滑，用户看到的就是「拖动的时候页面也跟着下滑」。
修法是把容器的**手势滚动**在拖动期间关掉（`scroll-y="{{!rowDrag.active}}"`），
而保留编程滚动：

```
实测（无头 Chrome，关闭 overflow-y 后）：
  关闭后位置保留（scrollTop 不被重置）：是
  关闭后仍可编程滚动（scroll-top 仍生效）：是
```

这一条很关键：边缘自动滚动（`autoScrollStep` → `setData({panelScrollTop})`）与
落点换算（`scrolledPx`）都依赖 `scroll-top`，所以不能改用 `catchtouchmove` 之类
「一刀切」的拦法把滚动一起废掉。`rowDrag.active` 一旦残留为 `true`，列表就再也滚不动，
因此 `abortRowDrag()` 在抬手、取消、切面板、页面卸载四条路径上都做了兜底复位。

### 代码包体积

开发者工具会把项目目录下**所有未被 `project.config.json` 的 `packOptions.ignore` 排除的文件**算进代码包。
开发期产物（无头 Chrome 的 profile、仿真 HTML、npm 缓存、`node_modules`）动辄数百 MB，
一旦漏配，主包会瞬间越过 1.5MB 上限——而且只在「代码质量」扫描时才暴露。

当前配置排除了 `node_modules`、`.work`、`.npm-cache`、`.npm-logs`、`.git`、`tools`
以及 `.md/.cjs/.mjs/.log/.DS_Store` 后缀，代码包实际只有 **277 KB**：

| 项 | 体积 | 上限 | 余量 |
| --- | --- | --- | --- |
| 主包（42 个文件） | 277.4 KB | 1536 KB | 1259 KB |
| 图片与音频资源 | 13.9 KB | 200 KB | 186 KB |

`npm run check:package` 会持续守住这条基线。

### 几何校验为什么值得单独做一层

「屏幕上是 2 页，导出却是 1 页」「智能一页压了参数但版面没变」——这类问题在网页版里靠肉眼
很难稳定发现。`check-geometry.cjs` 把纸张在浏览器里排版出来后，用
`getBoundingClientRect()` 量出每个区块 / 条目 / 栏位的坐标与尺寸，与引擎的预测逐个比对，
误差超出阈值就失败。

为了让比对有意义，脚本会先在页面里用 canvas 量出一张字体宽度表注入引擎
（`layout.setMeasureOverride()`），使两边使用同一套字体度量——否则测出来的是字体差异，
而不是排版规则差异。

**这套验证在开发过程中真的抓到了 4 个 bug**（都已修复，修复说明写在对应代码的注释里）：

1. `pages/templates` 把原始简历而不是编译后的 VM 传给纸张组件 → 缩略图整片空白
2. `styleOf()` 给 `font-weight` 之类的无单位值也补了 `px` → 被浏览器判为非法声明整条丢弃，
   侧栏姓名不粗、行距不生效（且不报任何错）
3. 双栏布局的列宽口径：`grid-template-columns: 1fr R%` 里百分比列是**内容盒宽度**、
   第 1 列不扣 gap，此前「先减 gap 再乘比例」导致左栏宽 9px、右栏窄 13px
4. 双线标题 `.th-double` 用 `!important` 把边框钉成 1px，引擎却按 3px 估算，
   每个区块多算 2px，6 个区块累积 10px——刚好够让分页判定与实际排版错开

### 后续审计抓到的缺陷（均已修复并补上断言）

对代码做了一轮专门的审计，其中几个是**用户一眼就能撞上、但一直没有任何测试覆盖**的：

1. **导出必崩（P0）**：`render.js` 的 `drawSectionTitle` 在 `line` / `double` 主题下读
   `titleBox.size`，而这两种主题的 `titleBox` 恒为 `null`。默认主题恰好就是 `line`，
   所以「打开标题居中 → 导出长图」100% 抛 `TypeError`。
   顺带修掉同一函数里 `fillRect` 画两遍的问题——第一遍用的是上一次遗留的颜色，
   `tint` 的半透明底色会因此偏色。
2. **纸面点击实际失效（P0）**：界面承诺「点纸面任意文字即可编辑」，但 `paper.js` 的
   `onTap` 只读 `e.target.dataset`。小程序里 `e.target` 是**被点到的最内层节点**，
   而 `dataset` 不做继承：点字形时事件源是文字节点（无属性 → `{}`），
   点栏位空白拿到 `{field}` 却缺 `sec/item`——两者都被守卫拦掉。
   唯一能生效的是点到条目节点自身暴露的背景，而 ONE 型条目的栏位铺满整行，暴露面积≈0。
   修复：`section.wxml` / `side.wxml` / `paper.wxml` 给文字叶子也挂上同一组 `data-*`，
   `onTap` 增加 `currentTarget` 兜底，叶子加 `pointer-events:none`。
   **之所以长期没被发现**：`check-logic.cjs` 此前直接手工构造 `onPick({detail})`，
   绕过了组件里的 `onTap`；浏览器仿真页又不输出 `data-*` 属性。
3. **落盘失败却谎报成功（P1）**：`writeDrafts()` 写失败返回 `false`，但 `save()` 不检查，
   照样把 `dirty` 清成 `false`、`savedAt` 设为当前时间。存储写满时界面显示「已保存 14:30」，
   退出后改动全丢，而且此后**再也不会重试**（`dirty` 已是 false）。
4. **`dirty` 判定口径不一致（P1）**：`snapshotJson()` 明确排除 `updateDatetime`，
   但 `refreshDirty()` 拿完整 JSON 比较。于是「改一个字 → 撤销回原样」之后 `dirty` 误报 `true`，
   界面一直挂着「未保存」，退出时还多做一次无意义落盘。
5. **照片文件只增不减（P1）**：每次选图都往 `USER_DATA_PATH/photos` 复制一份，
   而全项目没有任何删除逻辑——反复换照片会持续占用用户目录配额，
   最终把 `setStorageSync` 挤到写失败（即上面第 3 条）。现按「是否仍被任一草稿引用」回收。
6. **照片宽度联动是 no-op（P2）**：`onPhotoSize` 先写入新宽度、再用**新宽度**求比例算高度，
   结果恒等于原高度；整段联动没生效，还白多触发一次 store 广播。
7. **导出超出画布上限（P2）**：iOS 的 canvas 后端约 4096×4096 / 1670 万像素封顶，
   而 2 倍高清只够约 1.8 页 A4。超过后 `canvasToTempFilePath` 会失败或产出空白图。
   现在按上限自动下调倍率，并在降倍率时如实告知用户。
8. **智能一页的提示语与事实矛盾（P2）**：`mode === 'shrink' ? '已压缩到一页' : '已铺满一页'`
   把 `tight`（压到下限仍放不下）也归到「已铺满一页」。于是「2 页内容、参数压到底、
   结果还是 2 页」时会告诉用户「已铺满一页」，而屏幕上明明白白写着「共 2 页」。
9. **用户取消被报成故障（P2）**：拒绝相册授权时 toast「导出失败：已取消」，
   把用户自己的选择说成系统故障。
10. **模板库有 2 套模板筛不到（P2）**：分类写死 9 个，而模板实际用到 16 个 tag，
    「现代侧栏」「暖调创意」（tags 均为 设计/运营/市场）在任何具体分类下都不显示。
    改为从模板 tag 自动派生分类，并补上分类空状态。
11. **预览与导出横向错位一整列（P2）**：`renderedFields()` 漏了 `editable` 这一维，
    只读态仍按类型补出空栏，与 WXML 的 `usesCol()` 在 24 种组合里有 17 种不一致。
    最典型的是 THREE 条目只填正文时，屏幕落在第 1 列、引擎算在第 2 列，**差 331px**。
    详见上文「屏幕与导出必须同源」。
12. **导航栏标题偏左 72.5px（P2）**：标题用 `flex:1 + text-align:center`，可居中线是
    「左返回键 ~ 右按钮」之间而非屏幕中心，右侧还要为胶囊让位约 104px；而且
    「导出」变「导出中」时标题会再抖 7px。改为绝对定位居中，并让操作按钮提层压在标题之上
    （窄屏上两者几何必然重叠，保证按钮始终可点比让标题完整更重要）。
13. **「清空全部简历」清不干净（P1）**：`clearAll()` 与「删除最后一份」都在清空列表之后
    紧接着调 `save(true)`，而 `save()` 的语义是「把当前简历写进草稿列表」——它会拿
    `state.resume` 去 `unshift`，于是刚清空的列表**立刻被塞回一份示例简历**，
    用户看到的是「点了清空，简历还在」，删最后一份同样删不掉。
    更隐蔽的是 `init()` 只判断「列表为空就播种示例」，不区分「第一次使用」与
    「用户主动清空过」，所以即使绕过前者，清空后一重启示例简历又会回来。
    现在：`clearAll()` / `remove()` 停在空态且不再调 `save()`（同时清掉 `pb_current_v1`），
    `init()` 以「存储里是否写过 `pb_drafts_v1`」区分首次使用与主动清空——
    前者才播种示例，后者保持空。空态下 `state.resume` 仍有内存中的默认简历，
    「新建」与空态页照常可用，只是不落盘、不进草稿列表。

同时修掉的一批显示与交互问题：`page` 未声明为限高 flex 容器导致**底部面板被推到文档流末尾**
（必须滑到最底才看得见）；导航栏右侧按钮落在微信胶囊下方而**点不动**（按胶囊实测宽度让位）；
菜单从底部面板改为顶部浮层；工具栏 7 个入口等分保证全部可见（曾试过横向滚动，
但最右侧「菜单」会被挤出视野，入口藏起来比按钮窄更糟）；触控目标普遍提到 44px 以上
（`.tool` 高度 88→104rpx，`.btn-sm` 64→96rpx，导出按钮 72→96rpx，首页 `.hero-link` 从 17px 提到 48px）；
**按钮格式全项目统一**（见下节）；`--ink-3` 由 `#8a929c`（3.15:1）加深到 `#6b7280`（4.83:1）以满足 WCAG AA；
首页缩略图写死 `scale=0.28` 导致横向被裁 55%（只看得到简历中间一条），
模板页 `0.42` 在 320px 屏溢出 12%，均改为按容器实测宽度计算；导出时若内容过长
（超过 iOS canvas 约 4096px / 1670 万像素的上限）自动下调倍率并如实告知，
不再产出空白图；用户拒绝相册授权时提示「已取消」而不是「导出失败」；
选照片后回收不再被引用的旧文件，避免堆满用户目录把 `setStorageSync` 挤到写失败。

### 按钮格式统一（唯一定义在 `app.wxss`）

改前每个页面各写各的按钮行：`.btn-row` / `.hero-acts` / `.empty-acts` / `.tpl-acts` /
`.bar-right` / `.more` 六处，`gap` 在 12、14、16rpx 之间各取各的，而且**都不分配宽度**——
按钮宽度于是等于「文字宽 + 内边距」，同一排里宽窄不一，视觉上大小不一。

最典型的是编辑器浮层菜单底部：三个按钮挤在一个 flex 行里，「智能压缩到一页」7 个字
把行占满后，「新建简历」被挤到第二行、还短一截，看起来像三级不同的按钮。

现在按钮只有一套定义：

- **尺寸两级**：`.btn`（104rpx）/ `.btn-sm`（96rpx），两级都 ≥44px 触控下限，差值即「主 / 次」一档。
  圆角、字重、行高、纵向内边距全部一致，并统一 `white-space:nowrap`（换行会让同排按钮高度不齐）。
- **语义四种**：默认（白底描边）/ `.btn-primary` / `.btn-danger` / `.btn-ghost`。
- **排列三个容器**，页面内不得再自定义：
  - `.btn-row`：并列等分（`flex:1 1 0` + `min-width:0`），宽度只由容器决定；
  - `.btn-row-auto`：按内容宽排列（顶栏「复制 JSON / 去编辑」这类就地操作），
    `.btn-row-center` 再叠加整体居中（首页单个「清空全部简历」）；
  - `.btn-col`：纵向堆叠各占整宽（照片面板两个操作）；
  - `.btn-grid`：两列等宽，配 `.btn-wide` 让主操作跨满整行
    （菜单底部「智能压缩到一页」、首页 hero「＋ 新建简历」）。

为什么等分之外还需要 `.btn-grid`：等分宽度是「容器宽 ÷ 按钮数」，一旦某个按钮的文案
比这一份还宽，`nowrap` 的文字就会溢出格子。实测两个真实场景——菜单浮层内宽 420rpx、
三个按钮等分只剩 129rpx，而「智能压缩到一页」需 182rpx；首页 hero 三个等分 110px，
而「＋ 新建简历」在大一号字号下约 112px。两处都必须「主操作独占一行 + 其余两列等分」。
网格用 `minmax(0, 1fr)` 而不是 `1fr`：后者的最小值是 `auto`，长文案会把列撑宽、两列不再等宽。

`check-editlayout.cjs` 第 6 节把这条规范固化成断言：在 **320px 最窄机型**下造真实按钮组合，
用 `Range.getBoundingClientRect()` 精确量「文字实际宽度 vs 按钮内边距之间的可用宽度」。
不用 `scrollWidth` 判定——`.btn` 是 flex 容器且 `overflow` 默认 `visible`，
文字被 `nowrap` 撑出内边距时 `scrollWidth` 仍等于 `clientWidth`，根本测不出溢出。

## 与参考站的约定保持一致

- **模板 = 一整套风格**：切换模板会同时改配色、字体、标题装饰、栏式、字号行距、页边距，
  但**不改变已填内容**。因此换模板得到的是确定的一套排版，而不是新旧模板的混合。
- **空栏只在该类型确实用这一栏时才渲染**：否则 ONE（整行）条目会凭空多出左右两个空行，
  把 23px 的条目撑到 180px 以上，且用户删不掉（数据里本就没有内容）。
- **末尾区块的 margin-bottom 不属于内容**：它只影响盒高，不参与分页判定。
- **判页容差 1px**（`PAGINATION_SLACK`）：吸收行高累加带来的亚像素误差，
  避免内容底边 1123.9px 被切出一张只有一两行的第二页。
- **编辑态与只读态的槽位高度必须一致**：编辑态空栏渲染占位文字（真实占一行），
  只读态不渲染（高度 0）。分页计算按模式区分，否则会出现「编辑 2 页、预览 1 页」。

## 已知限制

- **字体**：小程序与参考站一样使用系统字体栈（宋体 / 黑体 / 楷体 / 仿宋 / Times / Arial）。
  目标机器未安装对应字体会回退，跨设备效果可能略有差异。
- **照片裁剪**：不做参考站那种自绘裁剪框，改用系统相册 / 相机的裁剪能力；
  证件照比例通过「比例」按钮调整尺寸得到。
- **文档列表读取**：小程序无法读取任意本地 `.json` 文件（没有文件选择器），
  因此「导入」改为粘贴 JSON 文本，功能等价。
- **导出**：只有 PNG 长图与 JSON 备份，原因见「能力边界」。
